# `axi4lite_slave` — Design Specification

**Module:** `axi4lite_slave`
**Protocol base:** AMBA AXI4-Lite, defined normatively in *Chapter B1 ("AMBA AXI4-Lite") of the Arm AMBA AXI and ACE Protocol Specification, document ARM IHI 0022E*.



---

## 1. Interface Parameters

| Parameter    | Default | Description                                              |
|--------------|---------|------------------------------------------------------------|
| `ADDR_WIDTH` | 8       | Byte-address width exposed on `awaddr` / `araddr`          |
| `DATA_WIDTH` | 32      | Data bus width. (must be fixed at either 32-bit or 64-bit) |
| `NUM_REGS`   | 16      | Depth of the internal word-addressed register file         |

Internal word index: `word_idx = addr[ADDR_WIDTH-1:2]` (i.e. addresses are word-aligned; the two LSBs select the byte within a 32-bit word and are not used to index the register file).

## 3. Response Encoding

```
2'b00 = OKAY    (AXI_RESP_OKAY)   — access succeeded
2'b01 = EXOKAY  (AXI_RESP_EXOKAY) — not a legal response on AXI4-Lite, never generated
2'b10 = SLVERR  (AXI_RESP_SLVERR) — slave-detected error (address out of range)
2'b11 = DECERR  (AXI_RESP_DECERR) — reserved, generated by system not this slave
```

## 4. Channel Handshake Rules

### 4.1 General rules

The general Valid/Ready rules that apply to *every* channel (`AW`, `W`, `B`, `AR`, `R`), on both the master and the slave side:

1. VALID signals must be LOW during reset.
2. Once VALID is asserted, it must remain asserted, and the accompanying payload (address/data/control) must remain stable, until the rising clock edge after READY is seen HIGH.
3. Transfer occurs only on a clock edge where VALID and READY are both HIGH on that channel.
4. The transmitter must not wait for READY before asserting VALID (avoid deadlock).
5. The receiver may assert READY either before or after VALID. 

### 4.2 Specific rules for `AW`, `W`, `B`

#### Slave side
1. The slave must wait for `AWVALID`, `AWREADY`, `WVALID`, and `WREADY` to all have been asserted (AW and W handshakes both complete) before asserting `BVALID`.
2. The slave must not wait for `BREADY` before asserting `BVALID`. 
3. Whenever the slave asserts `BVALID`, `BRESP` must be either `OKAY` or `SLVERR`. 

#### Master side
- The master asserts `AWVALID` only when it drives valid address and control information; `AWREADY` (slave) defaults to HIGH by recommendation. (assumption property)
- The master asserts `WVALID` only when it drives valid write data; `WREADY` (slave) defaults to HIGH by recommendation. (assumption property)
- `AWVALID`/`WVALID` may arrive in either order or simultaneously. (cover property)

### 4.3 Specific rules for `AR`, `R`

#### Slave side
1. The slave must wait for both `ARVALID` and `ARREADY` to be asserted before asserting `RVALID`.
2. The slave must not wait for `RREADY` before asserting `RVALID`.
3. The slave asserts `RVALID` only when it drives valid read data.

#### Master side
- The master asserts `ARVALID` only when it drives valid address and control information; `ARREADY` (slave) defaults to HIGH by recommendation. (assumption property)
- The master may assert `RREADY` before or after `RVALID`. (cover property)

## 5. `axi4lite_slave` Implementation

This section specifies the concrete behavior implemented in `axi4lite_slave.sv` according the above rules.

### 5.1 Write channel

- `awready = !aw_hs_done`, `wready = !w_hs_done` — both default HIGH out of reset.
- `AWVALID`/`AWREADY` and `WVALID`/`WREADY` handshakes are accepted independently and in either order. Whichever completes first is latched (`awaddr_latched`, `wdata_latched`/`wstrb_latched`) and its `*_hs_done` flag set; `awready`/`wready` then deassert (drop to 0) until the write actually fires, so a second AW or W beat cannot be accepted while one half is still pending.
- Once both `aw_hs_done` and `w_hs_done` are set (and no response is currently pending, `!bvalid`), the slave fires the write on the next clock edge:
  - If `word_idx = awaddr_latched[ADDR_WIDTH-1:2] < NUM_REGS`: for each byte `b` where `wstrb_latched[b]` is set, `regfile[word_idx][b*8+:8] <= wdata_latched[b*8+:8]`; `bresp <= OKAY`.
  - Else: no register is written; `bresp <= SLVERR`.
  - `bvalid` is asserted the same cycle `bresp` is computed, and `aw_hs_done`/`w_hs_done` are cleared, re-opening `awready`/`wready` for the next transaction.
- `bvalid` is deasserted the cycle after `bvalid && bready` (i.e. after the master accepts the response).


### 5.2 Read channel

- `arready = !rvalid` — HIGH by default out of reset; deasserts once `rvalid` is set and stays low until the master accepts the read data (`rvalid && rready`).
- On `arvalid && arready`: `word_idx = araddr[ADDR_WIDTH-1:2]`.
  - If `word_idx < NUM_REGS`: `rdata <= regfile[word_idx]`, `rresp <= OKAY`.
  - Else: `rdata <= '0`, `rresp <= SLVERR`.
  - `rvalid` is asserted the same cycle.
- `rvalid` clears the cycle after `rvalid && rready`.

### 5.3 Reset behavior

- On `!rst_n` (asynchronous assert): `aw_hs_done`, `w_hs_done`, `bvalid`, `rvalid` are all forced to `0`
- `bresp`/`rresp` are cleared to `2'b00`.
- `awready`/`wready`/`arready` are combinational function (!) of `*_hs_done`/`rvalid`, so they read HIGH immediately once `rst_n` deasserts.


### 5.4 Out-of-range access

- Write to `word_idx >= NUM_REGS` $\to$ `bresp = SLVERR`, register file unmodified.
- Read from `word_idx >= NUM_REGS` $\to$ `rresp = SLVERR`, `rdata = 0`.
